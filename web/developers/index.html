CyberSygn API. v1.

A REST API for the whole signing lifecycle.

Create a document, let CyberSygn find the signature fields, route it to your signers, and pull back the signed PDF and a tamper-evident audit certificate. One API key, server to server. The same detection and signing engine that runs the app, exposed for your code.

Embed

Add signing in five lines.

One script tag, one attribute. Any element with data-cybersygn-sign opens the full CyberSygn signing flow in an iframe modal on your own page. Point it at a signing_url from the create endpoint to have an API-created document signed in place, or at a PDF we host. No SDK, no build step, no dependencies.

The URL must be on cybersygn.io. The signing page fetches the document from our origin, and our connect-src 'self' policy blocks a PDF served from your own domain before the request leaves the browser. There is no proxy endpoint yet, so create the document through the API and embed the signing_url it returns.

<script src="https://cybersygn.io/embed.js"></script>
<button data-cybersygn-sign="https://cybersygn.io/preview/?doc=DOC_ID&t=TOKEN"
        data-cybersygn-source="your-app">
  Sign this document
</button>

Live demo, running on this page

Open it, and this line updates when a cybersygn:complete event arrives.

  1. Get a key. Keys are issued by hand today: email hello@cybersygn.io from your account email. The widget itself loads without one; the key is for POST /api/v1/documents, which returns the signing_url you hand to the button.
  2. Paste the snippet. Set data-cybersygn-sign to a signer's signing_url (signs that document in place) or to a PDF URL on cybersygn.io, such as a template under /templates-pdf/ (opens the send flow with the document preloaded). A PDF on your own domain will not load.
  3. Listen for completion. When the signer finishes, the widget fires a DOM event on window with the same payload the signing page posts:
window.addEventListener("cybersygn:complete", (e) => {
  // e.detail = {
  //   type: "cybersygn:complete",
  //   docComplete: true,          // every signer done?
  //   docId: "doc_abc123",
  //   signerEmail: "ada@example.com"
  // }
});

Optional attributes: data-cybersygn-email and data-cybersygn-name pre-fill the signer, data-cybersygn-theme (light, dark, auto) and data-cybersygn-accent (a hex color) match the modal to your brand. Full details on the embed widget page.

Base URL #

Every endpoint lives under one host. All paths below are relative to it.

https://cybersygn.io/api/v1

Responses are JSON, except the document download and audit endpoints, which return a PDF. Timestamps are ISO 8601 strings. API access needs a paid plan.

Authentication #

Authenticate every request with an API key. Keys are account-bound: each key acts as the CyberSygn account it was issued for, so your plan limits, branding, and webhook config all apply automatically. Keys are issued by hand today: email hello@cybersygn.io from your account email and we will issue your key.

Pass the key as a bearer token (preferred) or in the X-API-Key header.

Authorization: Bearer cs_live_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx

Or:

X-API-Key: cs_live_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx

Live keys are prefixed cs_live_. Test-mode keys are prefixed cs_test_. We never store the raw key, only its hash, so a key is shown to you exactly once at creation. Store it somewhere safe and never commit it. A missing or invalid key returns 401 unauthorized. A key may only read and act on documents its own account created; touching another account's document returns 403 forbidden.

Create a document #

POST/api/v1/documents

Create a document and send it for signature in one call. Give it a source PDF and a list of signers. CyberSygn detects the signature fields for you when you do not supply them, then emails each signer a magic link and returns one signing_url per signer.

Body

  • pdf_base64: the source PDF as base64 (a data: prefix is stripped for you). Provide this or template.
  • template: a template slug from your library (see List templates). Provide this or pdf_base64.
  • signers: required array of { name, email, order }. At least one, up to 20. order is optional and defaults to array position.
  • fields: optional array of field objects. Omit it and CyberSygn auto-detects the signature, initial, date, and checkbox fields it finds in the PDF. Pass an explicit array to place them yourself.
  • assignments: optional map of fieldId → signerId. Omit it and every field is assigned to the first signer. Pass it for multi-party routing.
  • cc: optional array of email addresses to copy on the completed document.
  • signing_order: "parallel" (default, everyone can sign at once) or "sequential" (one signer at a time, in order).
  • title: optional document title.
curl https://cybersygn.io/api/v1/documents \
  -H "Authorization: Bearer cs_live_xxx" \
  -H "Content-Type: application/json" \
  -d '{
    "title": "Mutual NDA",
    "pdf_base64": "JVBERi0xLjcK...",
    "signers": [
      { "name": "Ada Lovelace", "email": "ada@example.com", "order": 0 },
      { "name": "Alan Turing",  "email": "alan@example.com", "order": 1 }
    ],
    "signing_order": "sequential"
  }'
const res = await fetch("https://cybersygn.io/api/v1/documents", {
  method: "POST",
  headers: {
    "Authorization": "Bearer cs_live_xxx",
    "Content-Type": "application/json",
  },
  body: JSON.stringify({
    title: "Mutual NDA",
    pdf_base64: pdfBase64,            // or: template: "non-disclosure-agreement"
    signers: [
      { name: "Ada Lovelace", email: "ada@example.com", order: 0 },
      { name: "Alan Turing",  email: "alan@example.com", order: 1 },
    ],
    signing_order: "sequential",
  }),
});
const doc = await res.json();
console.log(doc.id, doc.signers[0].signing_url);

Response 201

{
  "id": "doc_abc123",
  "status": "sent",
  "title": "Mutual NDA",
  "signing_order": "sequential",
  "field_count": 4,
  "detected_fields": true,
  "signers": [
    {
      "id": "s1",
      "name": "Ada Lovelace",
      "email": "ada@example.com",
      "status": "pending",
      "signing_url": "https://cybersygn.io/preview/?doc=doc_abc123&t=..."
    }
  ],
  "created_at": "2026-06-13T17:04:00.000Z",
  "status_url": "https://cybersygn.io/api/v1/documents/doc_abc123",
  "webhook_note": "Subscribe to doc.completed via your account webhook to be notified when all signers finish."
}
Field detection. When you omit fields, detected_fields is true in the response. Two different failures are reported differently, because you act on them differently: 422 no_fields_detected means we read the PDF and it genuinely has no signature fields, while 503 detection_unavailable means we could not parse it at all and are not claiming anything about its contents. Either way you can pass an explicit fields array to place them yourself.

Get a document #

GET/api/v1/documents/:id

Fetch a document's current status and per-signer state. This is the simplest way to track progress: poll it until status is completed (see Webhooks for the push-based alternative).

curl https://cybersygn.io/api/v1/documents/doc_abc123 \
  -H "Authorization: Bearer cs_live_xxx"
const res = await fetch(
  "https://cybersygn.io/api/v1/documents/doc_abc123",
  { headers: { "Authorization": "Bearer cs_live_xxx" } }
);
const doc = await res.json();
if (doc.status === "completed") {
  console.log("Ready:", doc.download_url);
}

Response 200

{
  "id": "doc_abc123",
  "status": "partially_signed",
  "title": "Mutual NDA",
  "created_at": "2026-06-13T17:04:00.000Z",
  "completed_at": null,
  "voided_at": null,
  "signers": [
    { "id": "s1", "name": "Ada Lovelace", "email": "ada@example.com",
      "status": "signed",  "signed_at": "2026-06-13T17:10:00.000Z", "order": 0 },
    { "id": "s2", "name": "Alan Turing",  "email": "alan@example.com",
      "status": "pending", "signed_at": null, "order": 1 }
  ],
  "download_url": null,
  "audit_url": null
}

Document status is one of sent, partially_signed, completed, or voided. Signer status is one of pending, signed, or declined. download_url and audit_url are populated only once the document is completed.

Download the signed PDF #

GET/api/v1/documents/:id/download

Returns the flattened, signed PDF bytes, the same document a signer receives. Only available once the document is completed; before that you get 409 not_completed.

curl https://cybersygn.io/api/v1/documents/doc_abc123/download \
  -H "Authorization: Bearer cs_live_xxx" \
  -o signed.pdf
const res = await fetch(
  "https://cybersygn.io/api/v1/documents/doc_abc123/download",
  { headers: { "Authorization": "Bearer cs_live_xxx" } }
);
if (res.ok) {
  const bytes = new Uint8Array(await res.arrayBuffer());
  // write bytes to disk / storage
}

Audit certificate #

GET/api/v1/documents/:id/audit

Returns the tamper-evident audit certificate for a completed document: who signed, when, from where, and the document fingerprint. Like the download, it is available only once the document is completed and returns 409 not_completed otherwise.

curl https://cybersygn.io/api/v1/documents/doc_abc123/audit \
  -H "Authorization: Bearer cs_live_xxx" \
  -o audit.pdf
const res = await fetch(
  "https://cybersygn.io/api/v1/documents/doc_abc123/audit",
  { headers: { "Authorization": "Bearer cs_live_xxx" } }
);
const auditBytes = new Uint8Array(await res.arrayBuffer());

Void a document #

POST/api/v1/documents/:id/void

Cancel an in-flight document so it can no longer be signed. A document that is already completed cannot be voided and returns 409 already_completed. Voiding an already-voided document is idempotent and returns its current state.

curl -X POST https://cybersygn.io/api/v1/documents/doc_abc123/void \
  -H "Authorization: Bearer cs_live_xxx"
const res = await fetch(
  "https://cybersygn.io/api/v1/documents/doc_abc123/void",
  { method: "POST", headers: { "Authorization": "Bearer cs_live_xxx" } }
);
const doc = await res.json(); // doc.status === "voided"

Voiding is recorded on the document, not enforced as its own error code. GET /api/v1/documents/:id keeps returning 200 with status: "voided", and /download or /audit on it returns 409 not_completed, because voiding never marks a document complete. The signer-facing magic link is what refuses a voided document outright.

Detect fields #

POST/api/v1/detect

Run field detection on a PDF without creating or sending anything. Useful to preview what CyberSygn would place, or to seed your own fields array. Pass pdf_base64 in the body.

curl https://cybersygn.io/api/v1/detect \
  -H "Authorization: Bearer cs_live_xxx" \
  -H "Content-Type: application/json" \
  -d '{ "pdf_base64": "JVBERi0xLjcK..." }'
const res = await fetch("https://cybersygn.io/api/v1/detect", {
  method: "POST",
  headers: {
    "Authorization": "Bearer cs_live_xxx",
    "Content-Type": "application/json",
  },
  body: JSON.stringify({ pdf_base64: pdfBase64 }),
});
const { count, fields } = await res.json();

Response 200

{
  "count": 1,
  "fields": [
    { "id": "f1", "type": "signature", "page": 1,
      "x": 120, "y": 640, "width": 200, "height": 36,

}

Check the key #

GET/api/v1/me

Sanity-check a key. Returns the account it resolves to, the key id, and the mode. Handy as a first call when wiring up an integration.

curl https://cybersygn.io/api/v1/me \
  -H "Authorization: Bearer cs_live_xxx"
const res = await fetch("https://cybersygn.io/api/v1/me", {
  headers: { "Authorization": "Bearer cs_live_xxx" },
});
const me = await res.json(); // { ok, account, key_id, mode }

Response 200

{ "ok": true, "account": "acct_123", "key_id": "key_abc", "mode": "live" }

Provision keys for your users (partners) #

There are two ways to access the API. Standalone customers who buy CyberSygn directly get a metered key, gated by their plan. A partner that builds CyberSygn into its own product gets one server-side partner master key (capability canProvision) and uses it to mint an individualized, unmetered key for each of its own users. Every tenant key is its own credential: isolated to its own account namespace, attributable, and revocable on its own. Keep the master key on your server and never expose it to end users. Partner master keys are minted from the owner console.

Mint a tenant key

curl -X POST https://cybersygn.io/api/v1/keys \
  -H "Authorization: Bearer $CYBERSYGN_PARTNER_KEY" \
  -H "content-type: application/json" \
  -d '{"tenant_id": "your-customer-123", "label": "acme"}'

Response 201

{
  "key": "cs_live_...",
  "key_id": "key_...",
  "tenant_id": "your-customer-123",
  "account": "p-yourname-your-customer-123",
  "unmetered": true
}

The tenant key is shown once: store it against your user and use it as that user's bearer token. List your tenant keys with GET /api/v1/keys; revoke one with DELETE /api/v1/keys and body {"key_id":"key_..."}. A tenant key cannot mint further keys.

Webhooks #

Rather than poll, configure a webhook URL on your account and CyberSygn will POST a JSON payload to it as the document moves through its lifecycle. Because keys are account-bound, your existing account webhook config applies to API-created documents automatically.

Events

EventFires when
doc.createdA document is created and sent for signature.
signer.completedAn individual signer finishes their part.
doc.completedEvery signer has finished and the document is final.

Payload

{
  "event": "doc.completed",
  "document": {
    "id": "doc_abc123",
    "status": "completed",
    "title": "Mutual NDA",
    "completed_at": "2026-06-13T17:20:00.000Z"
  }
}

On doc.completed, call GET /:id/download and GET /:id/audit to retrieve the signed PDF and certificate.

No webhook? Just poll. The simplest integration skips webhooks entirely: after you create a document, poll GET /api/v1/documents/:id on an interval until status is completed, then download. Webhooks are the efficient option, not a requirement.

Embedded signing #

Keep signing inside your own app. Every signer in the create response carries a signing_url, shaped https://cybersygn.io/preview/?doc=...&t=.... Drop it into an iframe and the full CyberSygn signing flow renders in place. No redirect to a third-party site.

<!-- src is the signer's signing_url from the create response -->
<iframe
  src="https://cybersygn.io/preview/?doc=doc_abc123&t=..."
  style="width:100%;height:90vh;border:0"
  allow="clipboard-read; clipboard-write; camera"
  title="Sign with CyberSygn">
</iframe>

When the signer submits their part, the signing page posts a message to the parent window so you can update your own UI. The exact payload:

window.addEventListener("message", (e) => {
  if (e.origin !== "https://cybersygn.io") return;
  if (e.data && e.data.type === "cybersygn:complete") {
    // e.data = {
    //   type: "cybersygn:complete",
    //   docComplete: true,          // false while co-signers remain
    //   docId: "doc_abc123",
    //   signerEmail: "ada@example.com"
    // }
    // close the modal, refresh status, etc.
  }
});

If you would rather not build the modal yourself, the hosted embed widget does it for you: the five-line snippet at the top of this page. It opens signing in a managed full-viewport iframe modal, verifies the message origin, re-dispatches the same payload as a cybersygn:complete DOM CustomEvent on window (in event.detail), and closes itself after completion. data-cybersygn-sign takes either a signing_url or a plain PDF URL.

See the embed widget docs for theming, programmatic CyberSygn.open() control, and prefill options.

Rate limits #

Limits are charged to the account behind the key, not to the key and not to your IP address. Minting a second key does not buy more budget, and calling from many machines does not spread the cost. Partner tenant keys each sit in their own account namespace, so one of your tenants can never spend another tenant's budget.

Budgets are weighted by what a route costs us, and each tier has its own bucket. A burst of status polls cannot lock you out of sending a document.

RoutesStandard keyPartner (unmetered) key
POST /documents, POST /detect. Each runs a full PDF parse.20 / min, 300 / hour60 / min, 1500 / hour
GET /documents/:id/download and /audit. May render a certificate.60 / min, 600 / hour180 / min, 3000 / hour
Everything else, such as GET /me and GET /templates.120 / min, 2000 / hour360 / min, 6000 / hour

An unmetered partner key gets a higher ceiling but is still limited. unmetered means you are not billed per document, not that capacity is unbounded.

Requests that fail authentication are limited separately, 30 per minute and 200 per hour per IP address, so a wrong key is throttled without affecting anyone who holds a valid one.

Every response tells you where you stand:

RateLimit-Limit: 20
RateLimit-Remaining: 14
RateLimit-Reset: 37
Retry-After: 37          # on a 429 only

{ "error": "rate_limited", "message": "Too many requests to /api/v1/detect. Try again in 37 seconds.", "retryAfterSec": 37 }

Back off using Retry-After rather than retrying immediately. If our counter store is unreachable the limiter fails closed and returns 429, so a retry loop with no delay will stay blocked.

Error codes #

Errors come back as JSON with a stable error code and a human message. Switch on the code, show the message.

{ "error": "not_completed", "message": "The document is not fully signed yet." }
HTTPCodeMeaning
400invalid_jsonThe request body was not valid JSON.
400invalid_pdfpdf_base64 did not decode to bytes.
400invalid_signer_emailA signer entry has a missing or malformed email.
400invalid_templatetemplate is not a valid slug.
400missing_sourceNeither pdf_base64 nor template was supplied.
400missing_pdfpdf_base64 is missing, or it is present but carries no payload, for example a bare data: prefix or only whitespace. On POST /api/v1/documents an empty payload usually surfaces as 503 detection_unavailable first, and reaches this code only when you also pass an explicit fields array.
400missing_signersAt least one signer { name, email } is required.
400too_many_signersMore than 20 signers on one document.
400missing_tenanttenant_id is required. POST /api/v1/keys only.
400missing_key_idkey_id is required. DELETE /api/v1/keys only.
400payload_too_largeThe whole JSON request body exceeds 36 MB. Usually a large fields array on top of a large PDF. Distinct from the 413 below, which is about the PDF alone.
401unauthorizedMissing, malformed, or revoked API key. A revoked key is not reported separately.
402multi_signer_requires_paidMore than one signer while the account behind the key is on the free tier, for example after a subscription lapses.
402subscription_inactiveThe subscription behind the key is not active, for example a failed payment in dunning, so the account is on the free monthly allowance and has used it up. Update the payment method to restore unlimited sending.
402free_tier_limitThe free monthly document allowance is used up. Same lapsed-plan case as above.
403forbiddenThe document belongs to a different account, or the key lacks partner provisioning rights on /api/v1/keys.
404not_foundNo document with that id, or no such /api/v1 route.
404template_not_foundNo template matches that slug, or the template is empty.
404key_not_foundNo tenant key matches that key_id. DELETE /api/v1/keys only.
409signed_unavailableThe document is complete but the canonical signed copy could not be produced, for example because the original bytes passed their retention window. /download only.
405method_not_allowedThat method is not allowed on that path.
409not_completedDownload or audit requested before every signer has finished. A voided document also reports this, because voiding never marks it complete.
409already_completedA completed document cannot be voided.
413payload_too_largeThe decoded PDF exceeds the 25 MB limit.
422no_fields_detectedThe PDF was read successfully and contains no signature fields. Pass an explicit fields array.
429rate_limitedThe account behind the key has passed a rate limit. The response carries Retry-After and RateLimit-* headers, and retryAfterSec in the body. See the limits below.
500internal_errorUnexpected server error, for example a storage failure while saving the document.
500render_failedThe audit certificate could not be rendered. Most often a document title or signer name carrying characters outside Latin-1. /audit only.
503detection_unavailableThe PDF could not be parsed server-side, so we cannot say what it contains. Retry, or pass an explicit fields array.
